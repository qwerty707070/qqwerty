## 1. Что реально сломано на живом сайте

### БАГ 1 — критический: данные админки не доезжают до публичных страниц

То, о чём вы написали: меняете IP в `/admin/design` — на сайте остаётся старое значение.

Почему так происходит (по убыванию вероятности, все варианты проверяются за 5 минут, см. раздел 2):

| № | Причина | Как выглядит |
|---|---|---|
| 1 | Настройки админки живут **в браузере** (`localStorage` / `zustand persist`), а сайт читает константу или другой стор | изменение видно только в вашем браузере; в другом браузере/инкогнито — старое значение |
| 2 | Страница **статически сгенерирована** (SSG/ISR, `export const revalidate`, `unstable_cache`) | значение обновится через N минут/часов или после нового деплоя |
| 3 | Два разных хранилища/ключа: админка пишет `site-config`, сайт читает `settings` | сохранение «успешно», но не там |
| 4 | Ответ API кэшируется CDN/браузером (нет `no-store`) | в админке новое, при перезагрузке старое (или наоборот) |
| 5 | Supabase: чтение анонимным ключом при включённом RLS → `select` возвращает пусто → код молча берёт дефолт | сохранение работает, чтение всегда отдаёт дефолтное значение |
| 6 | После сохранения не вызывается `revalidatePath` / `router.refresh()` | публичные страницы остаются в кэше до перезапуска |

**Тот же баг уже размножился на другие данные — это и есть доказательство, что проблема архитектурная, а не в одном поле.**

### БАГ 2 — высокий: три разных набора данных об одних и тех же привилегиях

Проверьте сами: откройте главную, `/privileges` и страницу уровня. Цифры не совпадают.

| Уровень | Главная страница | Список `/privileges` | Страница уровня |
|---|---|---|---|
| KING | «+3 возможностей» (в сумме 7) | «+2 возможностей» (6) | **«6 возможностей»**, в списке 6 пунктов |
| GOD | «+3» | «+2» | — (в блоке соседей «+3») |
| OPKA | «+3» | «+2» | в блоке соседей на `/privileges/downer` — «+3» |
| D.OWNER | «+4» (в сумме 8) | «+3» | **«7 возможностей»**, в списке 7 пунктов |
| D.MODER | — | «+1» | в блоке соседей на `/privileges/king` — «+2» |
| D.ADMIN | — | «+1» | в блоке соседей на `/privileges/downer` — «+2» |
| VAMPIRE | — | «+2» | в блоке соседей на `/privileges/king` — «+3» |

Итог: минимум **три независимые копии** одного и того же справочника. Любая правка в админке размножает расхождение.

### БАГ 3 — высокий: содержимое кейсов на главной не совпадает со страницей кейсов

| Кейс | «Топ награды» на главной | «Топ награды» на `/cases` |
|---|---|---|
| Супер (29 ₽) | 10 000 риликов · Привилегия KING · 2 500 риликов | 100 / 250 / 500 / 1 000 риликов · Легендарный кейс ×1 — **привилегии нет вообще** |
| Легендарный (49 ₽) | 15 000 риликов · D.MODER · GOD | 500 / 1 000 / 2 500 риликов · **RABBIT** · 5 000 риликов |
| Мега (79 ₽) | **D.OWNER** · 50 000 риликов · **OPKA** | 1 000 / 2 500 / 5 000 риликов · **VAMPIRE** · 10 000 риликов |

Плюс противоречие **внутри одной страницы**: описание Мега-кейса обещает «здесь лежат OPKA, D.ADMIN и 50 000 риликов», а список наград под ним показывает VAMPIRE и 10 000 риликов.

Для магазина с реальными деньгами это не косметика: покупатель платит за D.OWNER в Мега-кейсе, а получает шанс на VAMPIRE.

### БАГ 4 — средний: шансы наград не сходятся с заявленными 100%

На `/cases` у Супер-кейса заявлено «9 позиций · 100%», показано 5 позиций: 30 + 22 + 16 + 12 + 8 = **88%**. Остальные 4 позиции (12%) на странице не раскрыты, хотя текст обещает «все награды и шансы» и «все награды видны заранее». То же у Легендарного (8 позиций) и Мега (9 позиций).

### БАГ 5 — средний: живые показатели — заглушки, а не данные

- Главная: «Привилегий 14 / Кейсов 3 / **Онлайн —**».
- Блок подключения: статус «скоро», «данные с сервера —», «мост Minecraft не подключён».
- Карточка статуса на `/support`: онлайна нет нигде.

Счётчики «14 привилегий», «3 кейса», «9 пакетов риликов» вписаны в разметку. Добавите товар в админке — цифры на сайте не изменятся (тот же класс бага, что и IP).

### БАГ 6 — низкий: SEO-мусор

- `/sitemap.xml` отдаёт `lastModified` = **момент генерации** для всех URL (проверено: все даты `2026-10-25T00:05:23Z`). Поисковик не понимает, что страница менялась.
- В sitemap нет `/profile`, хотя `/support` ведёт туда ссылкой «Проверить заказ».
- `/cases`, `/relics`, `/rules`, `/support` имеют одинаковый `<title>` («KINGGRIEF — Твоя империя грифа») и одинаковое описание.

### БАГ 7 — низкий: округление цены за штуку в наборах

Мега, набор 2×: 139 ₽ → подпись «70 ₽ за кейс» (реально 69,5 ₽). 3×: 199 ₽ → «66 ₽» (реально 66,3 ₽). Считать надо вниз (`Math.floor`) или показывать «≈».

## 2. Как за 5 минут подтвердить причину именно вашего бага с IP

1. **Откройте сайт в другом браузере или в инкогнито.** Если там новый IP, а в вашем браузере старый — причина №1 (данные в `localStorage`), публичные страницы вообще не читают хранилище.
2. **Посмотрите, что отдаёт сервер:** `curl -s https://kinggrief.vercel.app/ | grep -o 'play[^"<]*'` и то же для `/api/settings` (если такой есть). Если HTML содержит новый IP, а браузер показывает старый — кэш/DOM.
3. **Поищите жёстко прописанный адрес в коде:**
   ```bash
   grep -rn "play\.kinggrief\.net" --include=*.ts --include=*.tsx .
   ```
   Больше одного совпадения вне файла настроек — это и есть баг.
4. **Поищите кэш и клиентские хранилища:**
   ```bash
   grep -rnE "revalidate|unstable_cache|force-cache|localStorage|persist\(|createJSONStorage" src app 2>/dev/null
   ```
5. **Проверьте заголовки:** `curl -sI https://kinggrief.vercel.app/api/settings | grep -i cache`. Если нет `no-store` — CDN имеет право отдавать старое.

## 3. Что сделано в этом репозитории

Собран рабочий проект (Next.js 14 App Router), в котором тот же сценарий работает правильно и проверяется автотестом.

```
lib/settings.ts          схема настроек + валидация (IP, порт, URL, e-mail, онлайн)
lib/settings-store.ts    ЕДИНЫЙ источник правды: Supabase или .data/settings.json + журнал изменений
lib/auth.ts              пароль + TOTP 2FA, подписанная httpOnly-кука, лимит попыток входа
lib/catalog.ts           14 привилегий; все «+N возможностей» ВЫЧИСЛЯЮТСЯ из одного массива
app/api/settings         GET no-store / PUT с проверкой сессии и валидацией
app/api/auth/*           вход/выход
app/page.tsx             главная: IP и статус читаются на каждый запрос (force-dynamic)
app/privileges           список + таблица сравнения (цифры производные)
app/privileges/[slug]    страница уровня: состав и счётчики из каталога
app/admin/login          вход в панель
app/admin/design         редактор настроек + журнал «кто, когда, с какого IP менял»
components/ServerAddressCard.tsx   клиентская синхронизация: 15 с, focus, BroadcastChannel
scripts/e2e-sync-check.mjs         автотест «поменял в админке → видно на сайте»
scripts/check-content-drift.mjs    защита от рецидива: падает, если IP снова захардкожен
supabase/schema.sql                таблицы site_settings + site_settings_audit
```

Ключевые решения:

1. **Одно хранилище.** Ни один компонент не хранит собственное значение IP/ссылок/версий.
2. **Свежесть по умолчанию.** `dynamic = 'force-dynamic'`, `fetch(..., { cache: 'no-store' })`, заголовки `no-store`/`Vercel-CDN-Cache-Control: no-store` на `/api/settings`.
3. **Сброс кэша после записи.** `PUT /api/settings` вызывает `revalidatePath('/', 'layout')`.
4. **Мгновенная синхронизация вкладок.** `BroadcastChannel('kg-settings')` + опрос при `focus`/`visibilitychange`.
5. **Валидация на сервере.** Невалидный IP/URL не сохраняется (422) и подсвечивается в форме; значение в хранилище не портится.
6. **Всё производное — вычисляется.** `capabilityCount()`, `cumulativeFeatureCount()`, `discountPercent()` — расхождение «+3 против 6 пунктов» невозможно.
7. **Журнал изменений.** Кто, когда, с какого IP, какие поля и «было → стало».
8. **Антирегресс.** `npm run check:drift` падает, если в компоненты снова вписали домен или «N возможностей» руками.

## 4. Как перенести фикс в ваш проект (пошагово)

### Шаг 1. Свести настройки в одну таблицу

Supabase → SQL Editor → выполнить `supabase/schema.sql` из этого репозитория.
В Vercel → Settings → Environment Variables добавить:

```
ADMIN_PASSWORD=<свой пароль>
ADMIN_SESSION_SECRET=<32+ случайных символов>
SUPABASE_URL=https://xxxx.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<service_role, НЕ anon>
# ADMIN_TOTP_SECRET=<base32>   # если нужна 2FA
```

> Частая ловушка: чтение анонимным ключом при включённом RLS возвращает пусто, и код молча берёт дефолт. Поэтому запись и чтение — только `service_role` на сервере.

### Шаг 2. Заменить все копии значения одним чтением

Удалить из компонентов захардкоженные `play.kinggrief.net`, `discord.gg/...`, `@kinggrief.net`, счётчики. Оставить только `lib/settings.ts` (настройки) и `lib/catalog.ts` (товары).

Проверка: `npm run check:drift` → должно быть «✓ Рассинхрона нет».

### Шаг 3. Заставить страницы читать хранилище на каждый запрос

```ts
// app/page.tsx
import { getSettings } from '@/lib/settings-store';
export const dynamic = 'force-dynamic';
export const revalidate = 0;

export default async function Page() {
  const settings = await getSettings();   // свежие данные на каждый запрос
  ...
}
```

Убрать `export const revalidate = 60/3600` и `unstable_cache` вокруг настроек, если они есть.

### Шаг 4. Сбрасывать кэш после сохранения

```ts
// app/api/settings/route.ts (PUT)
const result = await saveSettings(payload, 'admin', clientIp(request.headers));
if (result.ok) {
  revalidatePath('/', 'layout');       // публичные страницы
  revalidatePath('/privileges');
}
return NextResponse.json(result, { headers: { 'Cache-Control': 'no-store' } });
```

### Шаг 5. Дать публичной странице самокорректироваться

Готовый компонент: `components/ServerAddressCard.tsx` (опрос 15 с + `focus` + `BroadcastChannel`). Он же показывает «данные синхронизированы в HH:MM», чтобы устаревшее значение нельзя было принять за актуальное.

### Шаг 6. Закрыть админку

- пароль и код 2FA сравнивать через `timingSafeEqual` (готово в `lib/auth.ts`);
- кука `httpOnly`, `sameSite=lax`, `secure` в production, срок 8 часов;
- лимит 5 попыток за 10 минут на IP;
- выход — только POST;
- журнал входов и правок с IP.
