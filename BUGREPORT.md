## 1. Почему «сохранение не работает» — найдено 6 причин, все воспроизведены

Жалоба «сохраняю в админке — ничего не происходит» воспроизведена на сборке и разобрана
по причинам. Каждая исправлена и покрыта тестом.

| № | Симптом | Причина | Исправление |
|---|---|---|---|
| 1 | Вход «проходит», но сохранение отвечает 401 и форма молча выкидывает на логин | Кука сессии ставилась с флагом `Secure` по одному лишь `NODE_ENV === 'production'`. По HTTP (локальный `next start`, preview-домен, доступ по IP) браузер такую куку **выбрасывает** | `sessionCookieOptions(request)` включает `Secure` только при реальном HTTPS (`x-forwarded-proto`), локальные хосты — исключение. `lib/auth.ts` |
| 2 | Сохранение одного поля → 422 «Ожидается текст» на всех остальных | Сервер требовал **полный** объект настроек | `PUT` принимает частичный payload и мержит с текущими значениями (`saveSettings` → `{...current, ...patch}`) |
| 3 | «Не удалось сохранить настройки» без деталей | Запись в `cwd` на serverless падает (`EROFS`/`ENOTDIR`), а ошибка не различалась | Каскад хранилищ: Supabase → файл → **файл в `os.tmpdir()`** с флагом `degraded`; в ответе `code` + `hint`, в админке — панель диагностики. `lib/settings-store.ts` |
| 4 | Сохранение прошло, но на сайте и в админке старое значение | Ошибка чтения Supabase (неверный ключ, RLS, нет таблицы) **молча** подменялась значениями по умолчанию, а запись падала в общий 500 | Ошибки чтения/записи различаются кодами (`SUPABASE_NO_TABLE`, `SUPABASE_UNREACHABLE`, `NO_WRITABLE_STORAGE`), каждый — со своим `hint`; публичная страница при сбое рендерится, но админка честно показывает проблему. Самодиагностика `POST /api/settings/verify` делает реальный круг «запись → чтение» |
| 5 | Поле «Порт» залипало, форма отправляла мусор | `Number('')` и `Number('12a')` → `NaN`, значение оставалось в состоянии и уходило в запрос | Числовые поля хранятся строками, в состояние попадают только цифры, пустая строка → `null`. `components/admin/SettingsForm.tsx` |
| 6 | Два админа сохраняют одновременно — правки одного тихо теряются | Нет проверки версии | Оптимистическая блокировка по `updatedAt`: ответ **409** + выбор «Загрузить свежие» / «Перезаписать моими» |

Дополнительно найдено и исправлено при написании тестов:

- **Адрес вида `mc.example.net:25566` сохранялся как `mc.example.net:25565`**, потому что отдельное
  поле порта перекрывало порт из строки. Со стороны — «сохранение не применяется». Теперь порт из
  адреса имеет приоритет (`splitHostPort` + правило приоритета в `validateSettings`).
- **Ссылка «Выйти» была POST-формой без CSRF-защиты** — заменена на кнопку с явным запросом;
  матчер middleware переписан без регулярки, которая молча не срабатывала.

Мега 2× за 139 ₽ подписан как «70 ₽ за ключ» (реально 69,5). **Исправлено:** `pricePerKey()`

### БАГ 11 — счётчики на главной вписаны руками

считаются из `PRIVILEGES.length`, `CASES.length`, `RELIC_PACKS.length`.

### БАГ 12 — цена из браузера не проверялась

Классическая дыра магазина: подмена суммы в запросе. **Исправлено:** `lib/pricing.ts`
пересчитывает корзину только по каталогу (price/name из запроса игнорируются), количество
ограничено, неизвестный товар — ошибка, а не бесплатный заказ. Покрыто тестами.

### БАГ 13 — SEO

`/sitemap.xml` отдавал `lastModified` = момент генерации (все URL с одинаковой датой «сейчас»),
`/profile` отсутствовал, у четырёх страниц одинаковый `<title>`.
**Исправлено:** `app/sitemap.ts` берёт дату из настроек (меняется при правке в админке),
`app/robots.ts` закрывает `/admin` и `/api`, у каждой страницы свой `metadata`.

Принципы, которые теперь выполняются:

1. Одно хранилище; ни один компонент не держит свою копию настроек.

7. Ошибки хранилища различаются кодами и содержат действие для админа.

## 5. Как перенести в ваш проект

### Шаг 1. Хранилище

Supabase → SQL Editor → `supabase/schema.sql`.
Vercel → Environment Variables:

```
ADMIN_PASSWORD=<свой пароль>
ADMIN_SESSION_SECRET=<32+ случайных символов>
SUPABASE_URL=https://xxxx.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<service_role, НЕ anon>
# ADMIN_TOTP_SECRET=<base32>   # если нужна 2FA
```

> Чтение анонимным ключом при включённом RLS возвращает пусто, и код молча берёт дефолт — самая
> частая причина «сохранил, а на сайте старое». Чтение и запись — только `service_role` на сервере.

### Шаг 2. Убрать копии значений

```bash
grep -rn "play\.kinggrief\.net" --include=*.ts --include=*.tsx .
```

Больше одного совпадения вне файла настроек — это баг. После переноса `npm run check:drift` должен
быть зелёным.

### Шаг 3. Страницы читают хранилище на каждый запрос

```ts
export const dynamic = 'force-dynamic';
export const revalidate = 0;
const settings = await getSettings();
```

Убрать `revalidate = 60/3600` и `unstable_cache` вокруг настроек.

### Шаг 4. Сохранение: частичный payload, версия, понятные ошибки

```ts
const result = await saveSettings(payload, 'admin', clientIp(request.headers), {
  expectedVersion, force,
});
if ('conflict' in result) return json({ code: 'VERSION_CONFLICT', current: result.current }, 409);
if (!result.ok) return json({ errors: result.errors }, 422);
revalidatePath('/', 'layout');
```

### Шаг 5. Клиентская синхронизация

Готовый `components/ServerAddressCard.tsx`: опрос 15 с + `focus` + `BroadcastChannel`, метка
«данные синхронизированы в HH:MM».

### Шаг 6. Диагностика вместо «ничего не произошло»

`/admin/design` → «Хранилище настроек»: бэкенд, путь, доступность записи, кнопка

### Шаг 7. Админка

## 8. «Всё равно не синхронизируется» — три реальные причины и как их отличить

Жалоба «меняю IP в админке, на сайте старое, а в админке IP пропадает» воспроизведена и
разложена на три независимых сценария. Каждый теперь либо исправлен, либо честно показан
в интерфейсе.

### Причина A (самая частая): непостоянное хранилище на serverless

На Vercel каталог проекта **только для чтения**: приложение вынуждено писать в `/tmp`.
`/tmp` не общий между инстансами и обнуляется при перезапуске. Что видит админ:

1. нажал «Сохранить» → ответ 200, значение показалось;
2. через минуту (запрос попал на другой инстанс) → старое значение;
3. на сайте — то, что лежит в *его* инстансе, то есть старое.

Это не баг кода, а отсутствие базы. **Решение:** `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`
(`service_role`, не `anon`) и `supabase/schema.sql`.

Что сделано, чтобы это не было загадкой:

- `POST /api/settings` возвращает `durable: false` и `warnings: ['NON_DURABLE_STORAGE']`;
- админка показывает красный блок «Сохранение не постоянное» с инструкцией;
- после сохранения тост предупреждает: «Сохранено только в этом инстансе»;
- страница `/admin/diagnose` ставит точный диагноз и пишет, что делать.

### Причина B: правка «исчезала» из-за блокировки версий

Раньше при расхождении `updatedAt` сервер отвечал **409** и не сохранял ничего. Если админка была
открыта до предыдущего сохранения (вторая вкладка, возврат «Назад», старая страница), любая правка
молча отклонялась — а после обновления страницы в форме оказывалось прежнее значение. Ровно
«обновлённый IP удаляется».

**Исправлено:** по умолчанию действует last-write-wins — правка применяется, а в ответе приходит
`warnings: ['VERSION_CONFLICT_RESOLVED']` с предупреждением в интерфейсе. Строгий режим остался
доступен явно (`strict: true` → 409) для тех, кому он нужен.

Дополнительно форма теперь:

- подхватывает новую версию с сервера, **если черновика нет**;
- если черновик есть — не затирает его, а показывает «на сервере более новая версия» и кнопку
  «Загрузить с сервера»;
- имеет кнопку «Обновить с сервера» в любой момент.

### Причина C: браузер показывал старую страницу

Если вернуться на вкладку сайта кнопкой «Назад», браузер восстанавливает DOM из bfcache — там
старый IP. Так же ведёт себя диск-кэш, если HTML отдавался без `no-store`.

**Исправлено:**

- заголовок `Cache-Control: no-store, must-revalidate` + `Vercel-CDN-Cache-Control: no-store`
  теперь на всех HTML-страницах, а не только на `/api/settings` (`next.config.js`);
- карточка адреса слушает `pageshow` (bfcache), `focus`, `visibilitychange`, опрашивает
  `/api/settings` каждые 10 секунд, имеет кнопку «Обновить»;
- в карточке видно состояние синхронизации: «данные синхронизированы в HH:MM», «нет связи с
  сервером», «устарели, обновляем…».

### Как отличить причину за 10 секунд

Откройте **`/admin/diagnose`**. Страница проверяет: доступно ли хранилище, проходит ли круг
«запись → чтение», **постоянное ли оно**, задан ли свой пароль, включена ли 2FA, читают ли
страницы хранилище на каждый запрос — и даёт вердикт с конкретным действием.

Если этой страницы на вашем домене нет — значит открыт старый деплой: локальные исправления
не могут попасть на него, пока не выложен код.
